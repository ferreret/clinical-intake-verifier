# clinical-intake-verifier

AI-assisted intake of clinical lab requests with a human in the loop. A request form is
scanned, a vision model extracts the fields, and an operator **verifies and corrects** instead
of transcribing.

The point is not the extraction. The point is the engineering stance around it:

> **The model is not the source of truth. It is one more source, and not the highest-priority one.**

When the model and the system of record disagree, the model does not win: the field turns red
and a person decides. Everything in this repository is built to be consistent with that idea:
systematic evaluation on every change, provenance on every field, and explicit handling of
uncertainty.

> Portfolio project by Nicolás Barceló, rebuilt from scratch from a real clinical digitisation
> problem. All data is synthetic and generated by the project itself. No real documents, no real
> patients, no real organisations.

F3 comes before the UI on purpose: without per-field metrics there is no way to know whether a
prompt change helped or hurt, and that is exactly what this project wants to show.

## Repository layout

```
schema/            single source of truth: field configuration, golden and prediction JSON Schemas
synth/             Python package (uv): generator (F1), evaluation harness (F3)
web/               Next.js app: extractor (F2), mock LIS, fusion engine, verification UI
docs/              design notes: golden format, extractor contract, evaluation, roadmap
data/synth/        generated documents (git-ignored, regenerate with one command)
data/runs/         extractor runs, one directory per run (git-ignored)
```

Real development documents never live inside the repository tree. `.gitignore` excludes
`/data/`, every PDF and image format, and `.env` as a second line of defence.

## Quick start: generate synthetic requests

Requirements: Python 3.12 and [uv](https://docs.astral.sh/uv/).

```bash
cd synth
uv sync
uv run intake-synth generate --n 50 --seed 42
```

This writes 50 PDFs, 50 golden JSON files, a `manifest.json`, the lab's test catalog
(`catalog.json`) and the lab's own records of patients, physicians and insurers (`lis.json`,
the mock LIS) into `data/synth/seed-42/`.
Same seed, same bytes on the same platform; on another operating system the content is the
same but the PDF bytes may differ (see [docs/golden-format.md](docs/golden-format.md#reproducibility)).
Useful options:

```
--scan-ratio 0.5          fraction passed through the scanner simulation (raster, skew, blur, grain, JPEG)
--handwriting-ratio 0.4   fraction with some fields written in a handwriting font
--templates lab-classic,insurer-form,hospital-compact
--only-index 17           regenerate one document, byte-identical to the batch
--out <dir>               output directory (default data/synth/seed-<seed>)
```

Check a golden visually, or validate a whole directory:

```bash
uv run intake-synth debug-boxes ../data/synth/seed-42/synth-000003.json
uv run intake-synth validate ../data/synth/seed-42
```

Run the tests:

```bash
uv run pytest
```

## Quick start: run the extractor

Requirements: Node 22 and a Gemini API key.

```bash
cd web
npm install
cp .env.example .env.local        # then put your key in GEMINI_API_KEY
npm run dev
```

`POST /api/extract` takes a multipart form with a `file` field and returns a prediction:

```bash
curl -F "file=@../data/synth/seed-42/synth-000003.pdf" http://localhost:3000/api/extract
```

To run it over a whole batch without the server:

```bash
npm run extract -- --in ../data/synth/seed-42 --limit 20
```

This writes one `<id>.pred.json` per document and a `run.json` into `data/runs/<run-id>/`,
reading only the PDFs. Running it again on the same directory skips documents already
predicted with the same model and prompt version, so a prompt change costs only what changed.

Compare a prediction with its golden visually, or validate a run directory:

```bash
cd ../synth
uv run intake-synth debug-boxes ../data/synth/seed-42/synth-000003.json --prediction ../data/runs/<run-id>/synth-000003.pred.json
uv run intake-synth validate ../data/runs/<run-id>
```

Tests, types and lint:

```bash
npm test && npm run typecheck && npm run lint
```

## Quick start: evaluate a run

```bash
cd synth
uv run intake-synth evaluate ../data/runs/<run-id>
```

This scores every prediction of the run against its golden and writes `report.json` and
`report.md` into `data/runs/<run-id>/eval/`:

```
eval 20261022-140331-gemini-3.8-flash-p2 vs data/synth/seed-42
  documents : 5 evaluated, 0 failed, 0 rejected, 195 of the source not in this run
  fields    : precision 100.0%  recall 100.0%  invented 0/19   46 correct, 0 wrong, 0 missed
  tests     : P 100.0%  R 100.0%  F1 100.0%  exact list 5/5
  boxes     : located 92/93 at IoU>=0.5, median 0.74
  warnings  : 0
  cost      : 8.8 s/doc, 2479 in / 1044 out tokens per doc
  worst     : none
```

Every field of every document is correct, wrong, missed, a correct null or **invented**, and the
report gives precision, recall and invention rate per field, test-list metrics, box
localisation, warnings, failures by error code, and the same metrics sliced by scan, template,
page count and handwriting, ending with the full list of mismatches. A failed API call is
counted as a failure, not as a worse model. Definitions are in
[docs/evaluation.md](docs/evaluation.md).

To see what a change did, compare the new run with an older one over the same goldens:

```bash
uv run intake-synth evaluate ../data/runs/<new-run> --baseline ../data/runs/<old-run>
```

The report then adds the change in every metric and the list of fields that were fixed and,
more importantly, the ones that broke.

## Quick start: fuse with the LIS

The fusion engine sets each document against the lab's own records and gives every field a
traffic light. Load the mock LIS, fuse, and score the result against each document's
scenario:

```bash
npm --prefix web run seed-lis -- ../data/synth/seed-42
npm --prefix web run fuse -- --golden ../data/synth/seed-42
cd synth && uv run intake-synth evaluate-fusion ../data/fusion/<fusion-id>
```

Without `--run`, every golden stands in for a perfect extraction; add
`--run ../data/runs/<run-id>` to fuse a real one. The two numbers that must stay at zero are
documents linked to the wrong patient and wrong values shown green. See
[docs/evaluation.md](docs/evaluation.md#fusion).

## Quick start: map tests to lab codes

Each requested line is mapped to the lab's codes: from what technicians approved before for
that insurer, then from a search of the catalog. A simulated technician replays a dataset in
order, approving and correcting, so the memory of approvals fills up as it would in use:

```bash
uv --directory synth run intake-synth generate --n 1000 --seed 42 --out ../data/synth/seed-42-n1000
npm --prefix web run map-simulate -- --dataset ../data/synth/seed-42-n1000
cd synth && uv run intake-synth evaluate-mapping ../data/mapping/<mapping-id>
```

The report is the learning curve: for each insurer, the share of lines proposed green and the
share the technician had to correct, from its first request to its hundredth. Green lines
still wait for the technician's approval; the number that must stay at zero is green lines
with the wrong codes. See [docs/evaluation.md](docs/evaluation.md#test-mapping).

## How the extractor works

**Two layers and a boundary.** The model is asked for a flat JSON in its own conventions
(boxes as `[ymin, xmin, ymax, xmax]` on a 0–1000 scale), with the field list and the prompt
generated from `schema/fields.json`. A boundary converts that into the prediction the rest of
the system consumes, with the same field keys and the same box shape as the golden, so that
evaluation needs no adapters. The boundary validates and annotates but never repairs: a date
that does not match its pattern stays as the model wrote it, flagged with a warning, for the
fusion engine and the operator to decide. Its one rewrite is mechanical and flagged too: a
title the model left in front of the physician's name is removed. Text the model garbled
(accented letters come back, now and then, as `Est\tevez` or `Ferr&#225;ndiz`) is detected,
flagged and the document is asked for again; it is never patched. Every prediction records
model, prompt version and input mode, so two runs are only compared when they were produced
the same way. The contract
is specified in [docs/extractor-contract.md](docs/extractor-contract.md) and enforced by
[`schema/prediction.schema.json`](schema/prediction.schema.json) on both sides.

## What the generator produces

**Multipage scans, the way they really arrive.** Most documents have several pages: the
request form itself (three templates, with long test lists continuing on a second page) plus
companion sheets in random order: the insurer's authorisation letter, a photocopy of the
insurance card and identity card, an informed-consent form filled in by hand, a fax cover
sheet, the blank back of a duplex scan, or the same form scanned twice. The request is not
always page 1, any field may sit on any page, and values repeat across sheets.

**Three templates** of Spanish lab request forms: a private laboratory form with a coloured
header and checkbox test list, an insurer authorisation form with cell layout and grouped test
profiles, and a dense monochrome hospital form with a patient sticker. Across documents the
generator varies date and identifier formats, drops optional fields, removes the insurer block
entirely, writes some fields in handwriting fonts, repeats the request number under a barcode,
adds distractors (record numbers with their own barcode, unticked pre-printed tests, diagnosis
text, observations, an identity card that prints F for mujer) and pushes half of the output
through a scanner simulation with per-page skew.

**Insurers write tests their own way, some in Catalan.** Tests are drawn from a synthetic lab
catalog of 726 coded tests, and each insurer prints them in its own wording ("GLU (SUERO)",
"S-Glucosa", "Glucèmia"); three insurers print the whole document in Catalan. Every test in
the ground truth carries the lab codes it means.

**A mock LIS to check documents against.** Patients and physicians come from the lab's own
records, and each document has a scenario: everything agrees, the phone changed since, the
form has a typo, the patient is new, or another patient has the same name. Load the records
into SQLite with `npm --prefix web run seed-lis` (after `npm --prefix web ci`).

Because the generator knows exactly what it drew, every document comes with its ground truth
for free: the value of each field, the verbatim printed string, page and bounding box of the
primary occurrence, every other location where the value appears, and whether it was printed
or handwritten. That is what makes evaluation runnable on every commit. The format is
specified in [docs/golden-format.md](docs/golden-format.md).

## Fields (v1)

`Paciente` · `FechaNacimiento` · `Edad` · `Sexo` · `DocumentoIdentidad` · `Telefono` ·
`NombreMedico` · `NumeroColegiado` · `NumeroPeticion` · `NombreMutua` ·
`NumeroSolicitudMutua` · `NumeroAutorizacion` · `NumeroTarjeta` · `tests[]`

Names, types, whether a field is mandatory and how it is compared are defined once in
[`schema/fields.json`](schema/fields.json) and read by both the Python package and the web app.

## Configuration

The repository runs without credentials except a Gemini API key for the extractor. See
[`web/.env.example`](web/.env.example) for that key and the optional model settings. The Python
package needs none; `INTAKE_SCHEMA_DIR` and `INTAKE_FONTS_DIR` can override where it looks for
the shared schema and the handwriting fonts.
