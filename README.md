# clinical-intake-verifier

AI-assisted intake of clinical lab requests with a human in the loop. A request form is
scanned, a vision model extracts the fields, and an operator **verifies and corrects** instead
of transcribing.

The point is not the extraction. The point is the engineering stance around it:

> **The model is not the source of truth. It is one more source, and not the highest-priority one.**

When the model and the system of record disagree, the model does not win: the field turns red
and a person decides. Everything in this repository is built to be consistent with that idea:
systematic evaluation on every change, provenance on every field, and explicit handling of
uncertainty.

> Portfolio project by Nicolás Barceló, rebuilt from scratch from a real clinical digitisation
> problem. All data is synthetic and generated by the project itself. No real documents, no real
> patients, no real organisations.

F3 comes before the UI on purpose: without per-field metrics there is no way to know whether a
prompt change helped or hurt, and that is exactly what this project wants to show.

## Repository layout

```
schema/            single source of truth: field configuration + golden JSON Schema
synth/             Python package (uv): generator (F1) and evaluation harness (F3)
web/               Next.js app: extractor, mock LIS, fusion engine, verification UI (F2+)
docs/              design notes and the golden format specification
data/synth/        generated documents (git-ignored, regenerate with one command)
```

Real development documents never live inside the repository tree. `.gitignore` excludes
`/data/`, every PDF and image format, and `.env` as a second line of defence.

## Quick start: generate synthetic requests

Requirements: Python 3.12 and [uv](https://docs.astral.sh/uv/).

```bash
cd synth
uv sync
uv run intake-synth generate --n 50 --seed 42
```

This writes 50 PDFs, 50 golden JSON files and a `manifest.json` into `data/synth/seed-42/`.
Same seed, same bytes. Useful options:

```
--scan-ratio 0.5          fraction passed through the scanner simulation (raster, skew, blur, grain, JPEG)
--handwriting-ratio 0.4   fraction with some fields written in a handwriting font
--templates lab-classic,insurer-form,hospital-compact
--only-index 17           regenerate one document, byte-identical to the batch
--out <dir>               output directory (default data/synth/seed-<seed>)
```

Check a golden visually, or validate a whole directory:

```bash
uv run intake-synth debug-boxes ../data/synth/seed-42/synth-000003.json
uv run intake-synth validate ../data/synth/seed-42
```

Run the tests:

```bash
uv run pytest
```

## What the generator produces

**Multipage scans, the way they really arrive.** Most documents have several pages: the
request form itself (three templates, with long test lists continuing on a second page) plus
companion sheets in random order: the insurer's authorisation letter, a photocopy of the
insurance card and identity card, an informed-consent form filled in by hand, a fax cover
sheet, the blank back of a duplex scan, or the same form scanned twice. The request is not
always page 1, any field may sit on any page, and values repeat across sheets.

**Three templates** of Spanish lab request forms: a private laboratory form with a coloured
header and checkbox test list, an insurer authorisation form with cell layout and grouped test
profiles, and a dense monochrome hospital form with a patient sticker. Across documents the
generator varies date and identifier formats, drops optional fields, removes the insurer block
entirely, writes some fields in handwriting fonts, repeats the request number under a barcode,
adds distractors (record numbers with their own barcode, unticked pre-printed tests, diagnosis
text, observations, an identity card that prints F for mujer) and pushes half of the output
through a scanner simulation with per-page skew.

Because the generator knows exactly what it drew, every document comes with its ground truth
for free: the value of each field, the verbatim printed string, page and bounding box of the
primary occurrence, every other location where the value appears, and whether it was printed
or handwritten. That is what makes evaluation runnable on every commit. The format is
specified in [docs/golden-format.md](docs/golden-format.md).

## Fields (v1)

`Paciente` · `FechaNacimiento` · `Edad` · `Sexo` · `DocumentoIdentidad` · `Telefono` ·
`NombreMedico` · `NumeroColegiado` · `NumeroPeticion` · `NombreMutua` ·
`NumeroSolicitudMutua` · `NumeroAutorizacion` · `NumeroTarjeta` · `tests[]`

Names, types, whether a field is mandatory and how it is compared are defined once in
[`schema/fields.json`](schema/fields.json) and read by both the Python package and the web app.
